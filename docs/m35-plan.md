# M3.5 迭代计划 · 可读性与流畅性

> 版本 v1.0 · 2026-10-26 · 上游：[`roadmap.md`](./roadmap.md) 任务 21b、[`next-iteration-plan.md`](./next-iteration-plan.md) W4/W6
>
> 本迭代只做两件事，且两件事都必须能被测量：
> **① 学生一眼能读懂画面在讲什么（R）；② 拖滑块、转视角不卡（P）。**

## 0. 问题定义（实测，不是转述）

### 0.1 流畅性：桌面没问题，问题在"没有降级能力"

`scripts/diag_fps.py`（本迭代新建）在本机 **Apple M4 / 2× DPR / 2095×1099 画布** 上跑全部 14 场景：

| 口径 | 结果 |
|---|---|
| P50 帧率 | 56.8–59.9 fps（中位 59.9） |
| P95 帧耗时 | 17.6–34.6 ms |
| 长帧（>50ms）占比 | 中位 **0.00%**，最差 1.09%（shm / buoyancy） |

再加压：3× DPR + 4 倍 CPU 降频，5 个重场景仍是 57–60 fps。

**结论有两层，第二层才是关键：**

1. 桌面端**没有可见卡顿**——所以任何"我看挺流畅"的判断都不是证据，也不能成为不优化的理由。
2. 4 倍 CPU 降频掉不下帧率 ⇒ **瓶颈不在 JS 主线程，在 GPU 填充率/带宽**（2095×1099 ≈ 230 万像素 × 泛光多 pass）。
   弱机（Mali-G57 / Adreno 610 级别）的差距正是填充率。
3. 而当前质量分级 `components/scene/quality.ts` 是**静态**的：只看窗口宽度和 DPR，
   一旦跑在 900px 以上的老平板上，它会判定 `high`，然后一直 high 到卡死。
   **没有运行时反馈 = 没有降级能力 = "会不会卡"取决于用户设备抽奖。**

### 0.2 可读性：矢量在屏幕上只有 1.4 像素粗

取 `baseline/projectile-motion.png`（视觉回归基线，不是随便截的图）：

- 相机到目标 42.6 世界单位，fov 45°，画布高 1099px ⇒ **0.032 世界单位/像素**。
- 矢量箭头默认 `radius = 0.022` 世界单位 ⇒ 半径 **0.68 px**、直径 1.4 px；锥形箭头（`radius×2.6`）高 1.8 px。
- 结果：抛体场景里 `v`/`vₓ`/`v_y` 三支箭头**在截图上根本不存在**，只剩三个文字标签浮在空中。
  学生看到的"速度"是一堆字母，不是矢量。

同一张图上还有三个可复现的排版缺陷：

| 缺陷 | 证据 | 为什么是缺陷 |
|---|---|---|
| 标签直接用 bind 名当下标 | 场景里写 `label: 'v_y'`，同场景 `vₓ` 却用了 Unicode 下标 | 同一画面两种下标排版，且下划线是代码泄漏到 UI |
| 标签只有名字，没有值 | `v`、`vₓ`、`v_y`、`g`、`F浮`、`N（测力计读数）` | 数值在右侧面板，学生要来回对位；**矢量可读性的本质是"长度=大小"**，没有数值就只能靠眼睛量 |
| 标签压在本体上 | buoyancy 的 `N（测力计读数）` 横跨水槽棱线 | 3D 里物体转动时标签随机遮挡，越关键的标注越容易被挡住 |

### 0.3 交互：拖滑块看不到变化

`engine/store.ts` 的 `setParam` 每次都写 `seekRequest: 0`：

```
拖动滑块 → t 被打回 0 → trail（依赖 t 采样）变空 → 只剩起点一颗球
```

抛体、洛伦兹、波动这些场景的**核心信息全在轨迹上**。于是"调参即真相"这句话在产品上不成立：
学生拖 `v₀` 看到的是同一颗球在起点抖，不是"v₀ 变大、射程变远"。

这与 Go/No-Go 第 2 条（平均调参 ≥3 次）直接冲突——**不是用户不愿意调，是调了没反馈。**

### 0.4 每帧分配（代码可查，不必测）

| 位置 | 现状 | 代价 |
|---|---|---|
| `SceneRuntime` | 每 55ms `{...scalars}`、`{...meta}`、`Object.fromEntries` + 每个序列 `slice(-120)` | 18 次/秒的对象与数组垃圾 |
| `SceneDust` | 700 粒子逐帧 CPU 循环 + 整个 position buffer 上传 | 每帧 8400B 上传 + JS 循环 |
| `DynLine` | 每帧 `geometry.setPositions()`（drei `Line` 内部重建 InstancedBufferAttribute） | 每帧新建 typed array + GPU buffer 重建 |
| `HighlightGroup.applyDimState` | 每帧 `traverse` + `material.needsUpdate = true` | 有触发着色器重编译的风险；0.35s ramp 内每帧一遍 |
| `SceneCanvas` | `preserveDrawingBuffer: true`，**全仓库无任何消费者**（无 `toDataURL`） | 白付一份帧缓冲拷贝，移动端尤贵 |

## 1. 两个支柱与验收判据

| 支柱 | 目标 | 判据（可执行） |
|---|---|---|
| **R · 可读** | 矢量的粗细、方向、大小在任何缩放与任何场景尺度下都读得出来；标注带数值与单位；标签不互相压、不压本体 | ① `v`/`vₓ`/`v_y` 等矢量在 1440×900 画布上**直径 ≥ 5px**；② 每个矢量标签含数值 + 单位；③ 标签重叠对数 = 0（自动布局单测）；④ `v_y` 渲染为真下标 |
| **R · 可理解** | 拖动任意参数，**同一时刻**的画面立即用新参数重算；上一组参数的轨迹以灰线保留做对比 | ① 拖 `v₀` 时轨迹持续可见且随参数形变（e2e 断言 canvas 像素差 > 阈值）；② 松手后 3s 内可见灰色前一条轨迹 |
| **P · 流畅** | 弱机自动降档，而不是一路卡死 | ① `diag_fps.py` 在 6× CPU 降频下能观测到降档发生（`data-quality` 从 high 变 mid/low）；② 三档的 DPR/泛光/阴影/尘埃可独立复现切换 |
| **P · 预算** | 守住宪法第七条 | draw call ≤150（`?diag=1` 实测）、单帧 JS ≤2ms、首屏 JS ≤200KB |

## 2. W1 · 渲染瘦身（约 2 天）

先削减每帧成本，再加自适应——顺序不能反，否则降档会把优化掩盖掉（降档后"看起来好了"，其实代码还是脏的）。

| # | 任务 | 做法 | 验收 |
|---|---|---|---|
| 1.1 | 关掉 `preserveDrawingBuffer` | 全仓无 `toDataURL`，基线脚本用 Playwright `element.screenshot`（走合成器，不读 drawingBuffer） | 基线 14 图零回归 |
| 1.2 | 尘埃 GPU 化 | 漂移写进顶点着色器（`uTime` uniform），去掉逐帧 JS 循环与 buffer 上传 | `SceneDust` 每帧 JS 开销归零；A/B 像素门 ≤0.5% |
| 1.3 | `SceneRuntime` 零分配 | 复用 `snapshot` 对象；series 用预分配环形缓冲，只在推 UI 时拷贝 | 堆增长曲线平（10s 内 ≤2MB） |
| 1.4 | `DynLine` 原地写 | 预分配 `instanceStart/End` 缓冲，每帧只改数组 + `needsUpdate` + `instanceCount` | 不再出现每帧新建 geometry（`renderer.info.memory.geometries` 恒定） |
| 1.5 | 压暗材料缓存 | `HighlightGroup` 挂载时遍历一次收集材质；只在 `transparent` 真翻转时置 `needsUpdate` | 0.35s ramp 内 0 次 `needsUpdate`（单测断言） |

## 3. W2 · 自适应画质（约 2 天）

| # | 任务 | 做法 | 验收 |
|---|---|---|---|
| 2.1 | `engine/perf.ts` 纯状态机 | 采样 rAF 间隔 → 中位数判定 → `high/mid/low` + 滞回（连续 2 个窗口才降，避免误判） | 纯函数单测：正常/慢帧/抖动/恢复 四组用例 |
| 2.2 | 接线三档 | `dpr` 2 / 1.5 / 1；泛光 开 / 半分辨率 / 关；阴影 1024 / 512 / 关；尘埃 700 / 300 / 关 | 三档截图可见差异，`?diag=1` 读到档位 |
| 2.3 | 降档提示（一次性） | 画布角落提示"已切换到流畅模式"，可点回高质量，选择记入 localStorage | e2e：6× 降频触发降档并出现提示；点一次后不再弹 |
| 2.4 | `?diag=1` 渲染统计 | `window.__p3d = { info, quality, frameMs }`，只在该参数下挂 | `diag_fps.py --diag` 输出 draw call / triangles / geometries |

> **降档优先级 = DPR → 泛光 → 阴影 → 尘埃**。依据 §0.1：4× CPU 降频不掉帧说明不是 JS 瓶颈，
> 所以先砍像素数（DPR 是二次方收益），再砍多 pass（泛光），最后砍固定开销（阴影/尘埃）。

## 4. W3 · 矢量与标签（约 3 天，本迭代的主战场）

| # | 任务 | 做法 | 验收 |
|---|---|---|---|
| 3.1 | 矢量屏幕恒定粗细 | 每帧按"箭头到相机距离 + 视口高度"换算 `worldPerPx`，`radius = clamp(radiusPx × worldPerPx)`；`vector.radius` 仍可覆盖 | 任意缩放/任意场景，箭头直径 5–7px；抛体三支箭头肉眼可见 |
| 3.2 | 标签就地读数 | `vector` 增 `valueBind`/`unit`/`digits`；标签两行：符号（下标）+ 数值单位；文本只在值变化时写 DOM，限 12Hz | 每个矢量标签含数值；DOM 写入次数 ≤12/s（e2e 计数） |
| 3.3 | 下标排版 | `engine/labelText.ts` 纯函数：`v_y` → `v<sub>y</sub>`，`F_net` → `F<sub>net</sub>`；HUD 与 3D 标签共用 | 单测 12 例；抛体场景不再出现下划线 |
| 3.4 | 标签避让 + 引线 | `engine/labelLayout.ts` 纯函数贪心分离（按优先级：矢量 > 文字 > 轴），被推开的标签画一条 SVG 引线回锚点 | 单测：10 个标签挤在 40px 内 → 0 重叠；视觉：buoyancy 的 `N` 不再压棱 |

## 8. 风险

| 风险 | 等级 | 对策 |
|---|---|---|
| 关 `preserveDrawingBuffer` 后某些截图变黑 | 🟠 中 | 基线用元素截图（走合成器）；`verify_*` 脚本全部先跑一遍，任一变黑立即回滚该项 |
| 尘埃着色器化改变观感 | 🟠 中 | A/B 像素门 ≤0.5%；`uTime` 用与原来一致的速度/幅度 |
| 标签自动布局抖动（每帧推来推去） | 🟠 中 | 位置写滞回（>6px 才动）；布局只在锚点变化超过阈值时重算 |
| 改参数不打回 0 破坏讲解脚本节奏 | 🔴 高 | 脚本走 `applyScriptParams`（本来就不重置），与用户 `setParam` 是两条路径；e2e 逐场景过一遍脚本 |
| 箭头变粗后遮挡小场景本体 | 🟡 低 | 粗细上限按视口 7px 封顶；buoyancy/shm 这类小场景逐帧看 |
| 每帧换算 `worldPerPx` 引入新开销 | 🟡 低 | 只在 Arrow 的 `useFrame` 里做一次 `distanceTo` + 乘除，无分配 |

### 10.3 这一轮挖出来的 6 个真 bug（计划里没写，实测撞出来的）

| # | 现象 | 根因 | 影响 |
|---|---|---|---|
| 1 | 整个画布像蒙了一层白纱，细线全灰 | **泛光阈值 0.88 低于底板亮度 0.955**，整块底板被当成高光做模糊叠加 | 42% 不透明度的轨迹峰值像素 `(143,190,199)` → `(222,225,226)`，相当于只剩 9%。历史结论"墨迹 0.3%、画面发灰"有一半是这个 |
| 2 | 画面一直"发虚" | 后处理管线 `composer` 没设 pixelRatio，整条管线（含场景 RenderPass）按 **1×** 渲染再放大到 2× | 相当于全站偷偷跑 dpr 1。修好是 4× 像素，靠长官僚兜底 |
| 3 | 矢量箭头被一个大圆盘盖住 | 锥体缩放把"轴向因子 × 径向因子"乘在一起 → 底圆放大 **36 倍** | 箭头方向完全读不出来 |
| 4 | 讲解步骤切换后轨迹消失 | 压暗下限 `0.14` 是照深色底调的，近白底上等于擦掉 | 聚焦一步 = 其余内容归零，10 秒测试必然判"没内容" |
| 5 | 拖滑块看不到变化 | `setParam` 每次 input 都 `seekRequest: 0`，轨迹依赖 t | 直接打击 Go/No-Go 第 2 条（平均调参≥3） |
| 6 | 跑久了越来越卡（隐患） | `DynLine` 逐帧 `geometry.setPositions()`，three 每次新建 `InstancedInterleavedBuffer` 且丢弃时不释放 | 260 点 × 60fps ≈ 每秒 60 个 GPU 缓冲只增不减 |

### 10.4 长官僚踩到的三个坑（已写进单测）

1. **热身只有 1.6s 不够**：buoyancy（玻璃透射 + 1024 阴影）头 3 秒是"每帧 33ms"的编译期，
   一台 M4 被判成中端机 → 热身改为按时长 3s，且**不设帧数下限**（1fps 机器要 60 秒才解冻）。
2. **大帧被当成"切标签页"**：1fps 软件渲染每帧都 >250ms，全被当断点丢弃 → 6 秒只数到 6 帧、一档没降。
   现在只有 `visibilitychange` 之后的那一帧才丢。
3. **严重档还要等两个窗口太慢**：<30fps 直接一步降到底，不等滞回。
