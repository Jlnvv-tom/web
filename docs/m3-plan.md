## 0. 本次调整（决策记录）

原 M3 是**商业化**：教师账号 / 班级作业 / 计价，假定"教师愿意为作业热力图付 149 元/年"。

现在改为**先把 3D 展示效果打磨到"值得分享"的水准**，理由三条：

1. **口碑传播是前置条件，不是结果。** 教师分享给同事的动作发生在"看到画面的 10 秒内"，
   不在"用了一个学期之后"。我们的商业化假设依赖教师推荐，而当前画面还撑不起推荐。
2. **Go/No-Go 第 2 条（平均调参 ≥3）测的是"愿意玩"。** 现在画面 82% 是纯黑虚空、
   没有投影、没有材质，用户"点开看三秒就走"的概率远高于"付费意愿不足"。
   先修这个，指标才有意义。
3. **商业化的沉没成本为零。** 后端一行没写，账号一个没做，顺延只是换个顺序，
   不影响任何已完成的东西。计划完整保存在 M4 文档里，随时可以捡起来。

> 一句话：**现在的瓶颈是"这东西看起来像不像一个产品"，不是"能不能收钱"。**

## 1. 诊断：我们到底差在哪

### 1.1 量化画像（12 个场景实测，与参考站对比）

把 12 个场景的默认帧降采样到 360×225，逐像素统计 HLS：

| 指标 | 我们（12 场景范围） | 参考站 Jelly Baby | 判读 |
|---|---|---|---|
| **平均亮度** L | **0.072 – 0.109** | **0.577** | 差 **6.8 倍** |
| 亮度标准差 | 0.065 – 0.135 | 0.111 | 我们的对比度全压在暗部 |
| **平均饱和度** S | **0.458 – 0.538** | **0.264** | 我们过饱和约 **1.9 倍** |
| **暗部占比**（L<0.08） | **68% – 90%** | **0%** | 没有中间调，只有黑和发光 |
| 高光占比（L>0.75） | 0.1% – 1.0% | 1.4% | 缺亮部 |
| 色相集中度 | 分散 4–11 个色相桶 | **92% 落在 0–60°（暖橙/木色）** | 我们没有统一色调 |

**三个结论**（都是反直觉的）：

1. **我们不是"不够多彩"，而是"过饱和 + 全黑"。** 均饱和 0.49 是霓虹色的量级；
   参考站只有 0.26。舒服的观感来自**低饱和 + 高亮度**，不是来自"更鲜艳"。
2. **参考站靠"统一色调"建立氛围，不靠对比色发光。** 它 92% 的像素在一个暖色相区间，
   只有主角果冻是绿——这才是"高级感"的来源。
3. **我们没有中间调。** 暗部 68–90% 意味着画面上除了发光线条几乎什么都没有，
   所以再多的 bloom 也只是"黑底上更亮的线"，不会变得"真实"。

### 1.2 六个具体缺陷（都能指到代码或数值）

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| D1 | **阴影从未生效** | `objects.tsx:656` 写了 `castShadow receiveShadow`，但 `SceneCanvas` 的 `<Canvas>` 没有 `shadows` 属性，4 盏灯无一设 `castShadow` | `castShadow` 是**死代码**；所有物体悬空，没有落点 |
| D2 | **没有可受光的地面** | `grid` 图元是 `LineSegments` 线框，不是 mesh | 无接触阴影、无反射、无"站在哪"的锚点 |
| D3 | **材质配方单一** | 实体只有 `metalness 0.55 / roughness 0.35` 一种；其余视觉信息全来自 `emissive` 线 | 物体像彩色塑料块，没有木/布/玻璃/石膏的层次 |
| D4 | **过饱和霓虹** | 均饱和 0.49，青 `#22d3ee` + 橙 `#ff8a3d` 高饱和对撞 | 廉价感；长时间看眼睛累 |
| D5 | **构图浪费** | `fov 45` + 目标点偏移，主体常只占画面 30–65%（`lever` 曾只占 30%） | 画面一半是空的黑 |
| D6 | **UI 挤压画布** | 画布上方 chip 排、右上按钮、左下提示条、右侧 312 px 参数面板 | 参考站 UI 只有 3 个 32 px 圆钮，画布占满视口 |

> D1 是最值得单独强调的：**这是"写了但没生效"的典型**。没有人会报 bug，
> 因为它不闪退、不报错，只是画面永远差一口气。这类缺陷只能靠"对照参考图找差异"发现。

## 2. 参考站读解

### 2.1 技术事实

抓取 pages 时它直接失败并打印：

```
Starting WebGPU
THREE.WebGPUBackend: Unable to create WebGPU adapter.
```

即：**three.js 的 WebGPURenderer**（`THREE.WebGPUBackend`），不是 WebGL。
配合实时软体（果冻的挤压/回弹、松手抖动），基本可以确定它走的是
WebGPU + compute/TSL 的路线，这也是它能做到"果冻质感 + 60fps"的原因。

### 2.2 能借什么、不能借什么

| 维度 | 参考站做法 | 我们的取舍 |
|---|---|---|
| 渲染后端 | WebGPU | ❌ **不跟**。校园机房/三年老机器/微信内置浏览器大面积不支持；宪法第七条要求中端安卓 ≥30fps。留在 WebGL2 |
| 实时软体 | 物理仿真驱动的形变 | ❌ **不跟**。宪法第五条要求 `sample(t)` 纯函数、宪法第一条要求物理正确；形变只能是**装饰层** |
| 暖调环境光 | 大面积柔和暖光 | ✅ **要**。这是"舒服"的第一来源，WebGL2 完全能做到 |
| 有落点的阴影 | 主光软阴影 + 接触阴影 | ✅ **要**。当前完全缺失（D1/D2） |
| 材质层次 | 半透明果冻/布/木/陶瓷 | ✅ **要**，但必须**程序化生成**（宪法第八条：零外部资源） |
| 微缩实景构图 | 一个"房间角落"，有参照物 | ✅ **要**，改成"一个小实验台" |
| 极简 UI | 3 个小圆钮 + 角落键盘提示 | ✅ **要**，HUD 收进抽屉 |
| 角色人格（小脸表情） | 果冻有脸 | ⚠️ **谨慎**。物理教具加表情容易滑向"玩具"，只在装饰性元素上试 |

## 3. 方向：深色展厅 + 暖色展台（The Lit Vitrine）

### 3.1 一句话

**页面外壳保持深色（现有 chrome 不动），画布内部变成"一盏灯打亮的小展台"。**

这个选择解决了一个真实矛盾：整体转浅色要重做全部 UI（成本高、风险大），
而画面不变又永远像工程 demo。折中方案是——**把"亮度"投资在舞台上，把"深色"留给边框**，
形成博物馆展柜式的对比：暗处更暗，亮处有质感。

### 3.2 顺带解决的课堂问题

**明亮教室里，投影仪打深色背景会发灰、对比度塌陷。** 一节上午的课，窗帘不拉，
深色画面在幕布上几乎看不清细节。浅暖色台面 + 高对比矢量，在投影环境里反而更稳。

所以这不是"为了好看"，是**课堂可用性**。这条也进了验收（见 §8 的投影模拟检查）。

### 3.3 三条美术原则

| 原则 | 内容 | 怎么检验 |
|---|---|---|
| **P1 · 万物有落点** | 每个立体物体必须落在某个面上，且有阴影或接触阴影 | 截图里找不到"悬空的实体" |
| **P2 · 三色 + 一材质** | 每个场景主色 ≤ 3 种，且至少 1 种真实质感材质（木/布/玻璃/金属/石膏） | 调色板统计 + 人工评审 |
| **P3 · 动则要有手感** | 会动的元素必须有缓动/挤压/回弹；但**形变不得作用于表示物理量的几何** | 关上"演出层"后，物理几何一字不变 |

> P3 是对宪法的落地：趣味可以加，但只能加在**不承载测量信息**的层上。
> 例如浮力场景可以让水花溅起，但方块的尺寸、浸入深度、力矢量的长度一点都不能变。

## 4. 美术规范 v1（可执行参数）

### 4.1 配色 token（新增，不改旧 token）

```css
@theme {
  /* 展台 */
  --color-stage-wood:   #E4D6BF;   /* 主台面：浅胡桃木 */
  --color-stage-linen:  #F0E9DC;   /* 亚麻布/纸面 */
  --color-stage-clay:   #D7C4AB;   /* 石膏/陶土 */
  --color-stage-shadow: #2A2119;   /* 接触阴影（暖黑，不是纯黑） */

  /* 环境（暖黑，替换现在的冷黑 #04070d 作为画布内背景） */
  --color-stage-backdrop: #1B1713;
  --color-stage-fog:      #221C16;

  /* 物理量强调色（从上调低饱和，但保持高对比） */
  --color-vec-cool:  #3FBFD4;      /* 场/速度 */
  --color-vec-warm:  #E8823F;      /* 力/加速度 */
  --color-vec-rose:  #D9709A;      /* 感应/次生量 */
}
```

关键变化：**饱和从 ~0.50 降到 ~0.28**，但**明度对比拉大**（亮台面 vs 暖黑背景）。
"看得清"靠明度对比，"好看"靠低饱和——这两件事之前被混成了"更鲜艳"。

### 4.2 材质配方库（6 种，全部程序化，零贴图文件）

| 材质 | 参数 | 程序化细节 | 用在 |
|---|---|---|---|
| `wood` | roughness 0.62 / metalness 0 / clearcoat 0.05 | 顶点色 + 正弦扰动生成木纹走向，或用 `CanvasTexture` 画 512 条细纹 | 台面、杠杆的杆 |
| `linen` | roughness 0.92 / metalness 0 | 用 `repeat` 的法线噪声（Canvas 生成）模拟布纹 | 背景布、斜面 |
| `clay`（哑光） | roughness 0.88 / metalness 0 | 无 | 实验器材底座、粉笔字块 |
| `glass`（半透明） | transmission 0.92 / thickness 0.4 / ior 1.5 / roughness 0.08 | 无 | 透镜、水、气泡 |
| `jelly`（半透明带次表面感） | transmission 0.65 / roughness 0.22 / clearcoat 0.6 | 内部加一层 `emissive` 微弱内发光模拟"透光" | 果冻、柔性物体 |
| `metal`（拉丝） | metalness 0.9 / roughness 0.28 | 各向异性朝向沿长边 | 钩码、极板、磁铁 |

> `transmission` 在 WebGL2 下是 `MeshPhysicalMaterial` 的屏幕空间折射，**每个材质一次额外 render target**。
> 性能预算见 §9：中低档降级为 `opacity` 半透明。

### 4.3 光照 rig（固定 4 灯 + 1 阴影）

```text
hemisphereLight  上 #FFF3E0 / 下 #3A2E24   强度 1.1    ← 大面积暖环境光，"亮"的主要来源
directionalLight 主光 (-4, 7, 6)  #FFF6EA   强度 2.6    ← 唯一投影光源，castShadow
directionalLight 冷补光 (6, 3, -5) #BFD8E8  强度 0.7    ← 拉开冷暖，避免画面发黄发闷
pointLight       台面补光 (0, 0.4, 0) 暖     强度 3.0   ← 让台面中心微微提亮（衰减 2）
```

阴影配置（性能与质量折中）：

```ts
shadows: 'soft'                    // PCFSoftShadowMap
shadow.mapSize: 1024               // 1024 足够，2048 在中端安卓掉帧
shadow.camera: 正交，覆盖台面 ±1.2× 尺度
shadow.bias: -0.0008 / normalBias: 0.02
```

> 当前 `Lights` 是 3 平行光 + 2 点光、无投影（§1.2 D1）。改成"1 主光投影 + 3 补光"，
> 视觉上立刻有落点，性能上反而更省（少一盏平行光）。

### 4.4 后处理（从"泛光堆氛围"改为"轻微收边"）

| 参数 | 现在 | 改为 | 原因 |
|---|---|---|---|
| `toneMappingExposure` | 1.15 | 0.95 | 台面变亮后需要压回，否则过曝 |
| bloom `strength` | 0.62 | **0.18** | bloom 只服务"发光体"（矢量箭头、粒子），不该给整个台面镀光 |
| bloom `threshold` | 0.60 | **0.85** | 只让真正的高光溢出，台面高光不参与 |
| bloom `radius` | 0.55 | 0.35 | 收细，避免糊 |
| 新增 · 暗角 | 无 | 可选 `vignette` 0.25 | 把视线收到台面中心 |
| 新增 · 接触阴影 | 无 | 每个场景 1 张贴图（Canvas 径向渐变） | 最便宜的"落地感" |

### 4.5 构图与取景规则（写死成约束，进契约测试）

1. **主体占画面高度 ≥ 62%**（现在有场景只有 30%）
2. **相机 target 必须在主体包围盒中心 ±15% 内**
3. **画布内必须有一块"台面"，且与水平面夹角 < 8°**（保证有明确的重力方向）
4. **至少 1 个参照物**：铅笔 / 直尺 / 硬币 / 手指轮廓，用于建立尺度感
5. **标签与箭头不得重叠主体超过 30% 面积**

> 前 4 条可以自动化（`shot_canvas.py` 已能量主体 bbox；台面倾角可从 spec 算；
> 参照物可以查 `objects` 里有没有 `ref-prop`）。第 5 条人工评审。

#### 4.5.1 规则修正记录（2026-10-24，`engine/contract/framing.test.ts` 落地时）

规则 1/2 已契约化，但**初版判据是错的**，实测后修正三处（理由写死，防再拍脑袋）：

| 初版判据 | 问题 | 改为 |
|---|---|---|
| 竖直占高 ≥ 62% | 宽扁型主体（透镜装置 7.8×1.68、绳波 4×1.2、抛体轨迹 40×10）天然受水平约束：竖直填满 62% 时水平溢出 130% | **max(竖直, 水平) 填充率 ≥ 62%**，另加 min ≥ 15% 防细带 |
| 覆盖率 ≤ 150% | 体积型主体（电场充满空间 191%、线圈特写 351%）刻意大于画面是合法构图 | **删除上限** |
| 投影包围盒中点居中 | 主体有深度起伏时（平面镜的物/像一前一后），远近端点在切线空间拉伸不对称，中点被拖离世界中心的投影（reflection 实测：世界中心投影偏 2.5%，包围盒中点报 25%） | **世界包围盒中心的屏幕偏移 ≤ 15%**，忠于规则原文；且主体溢出画面时**豁免居中**（看到的是局部，硬居中两边一起出画） |

修正后真实失败收敛到 7 个场景 26 处，全部通过修相机解决（不是放宽阈值）：
lorentz/projectile/thin-lens/shm 补相机距离，capacitor 微距 10%，
lever/em-induction 重瞄 target。修复后 84 断言全绿、645 测试全绿、
14 场景基线图重建。

## 5. 六条工作流

### W1 · 舞台与光照地基（1.0 周）

| # | 任务 | 验收 |
|---|---|---|
| 1 | `world.stage` 契约字段（`kind: 'none' \| 'table'`、`surface`、`size`、`referenceProp`） | 契约测试通过；不设该字段时行为与现在**完全一致**（零回归） |

| 3 | 新光照 rig（1 主光投影 + 3 补光） | 截图对比：物体有落点 |
| 4 | `Canvas` 开启 `shadows`（分档，见 §9） | 阴影真的出现（修复 D1 死代码） |
| 5 | 新的暖黑 backdrop + 雾色 | 画布内不再是纯黑 |

**这是唯一"改一次影响 12 个场景"的工作流，必须先做完、先验证。**

#### W1 实施记录（2026-10-22，已落地）

契约新增 `world.stage`（`kind` / `y` / `size` / `surface` / `backdrop` / `shadows` / `contact`），
不写该字段时行为与 M2 **完全一致**——所以 12 个场景可以逐个迁移、随时中断。
已迁移 3 个金标准场景，实测（纯画布口径）：

| 场景 | 均亮 | 暗部占比 | 均饱和 | 台面暗斑（投影） |
|---|---|---|---|---|
| `buoyancy` | 0.109 → **0.398** | 68.0% → **0.0%** | 0.476 → **0.280** | 1.2%，最深 0.24×中位 |
| `lever` | 0.081 → **0.487** | 83.3% → **0.0%** | 0.478 → **0.313** | 0.2% |
| `shm` | 0.079 → **0.338** | 83.1% → **0.0%** | 0.458 → **0.268** | 0.3% |

物理读数逐字节未变、0 console error、444 条测试全绿。
仍未达标的两项：`std_l` 约 0.15（目标 0.16+）、`bright_ratio` 0（目标 1.5%+）——
这两项都要靠 **W2 的材质高光**，不是 W1 能补的。

**W1 踩到四个坑，都值得记住：**

1. **ACES 会把背景色压到 1/3。** 写 `#2C231A`（sRGB L≈0.14）时屏幕上只剩 L≈0.043，
   比"暗部"阈值 0.08 还低，于是上半屏全被统计成暗部，怎么加台面都降不下来。
   补偿到 `#5A4B3A` 才落在 0.13 附近。**雾色必须用同一个值**，两边走同一条 tone mapping
   才能让远处物体刚好融进背景。
2. **CSS 暗角是隐形杀手。** 深色科技风那层 `rgba(2,5,10,0.55→0.9)` 的径向渐变，
   压在暖台面顶部会把 0.09 直接压到 0.046。展台场景几乎把暗角去掉。
3. **雾会把远处的台面吃掉。** 一开始以为是台面太小，把 `size` 从 1.28 加到 2.60 完全无效——
   因为 `camDist × 0.9 ~ × 4.2` 的雾把 3 m 外的台面染成了背景色。推到 `× 2.2 ~ × 9` 才露出台面。
4. **小物体靠真实投影压不住。** 摆球直径 4 cm、钩码更小，投影正好被自己挡住，
   画面仍然是"浮着"。所以需要单独的**接触阴影**贴图（`stage.contact`，米）。
   这条在计划 §4.4 里列过，实施后确认是必需的而不是可选装饰。

> 还有一个测量教训：**必须用纯画布截图（`shot_canvas.py`）而不是整页截图**。
> 整页图里的深色页头与右侧参数面板会把"暗部占比"拉高十几个百分点，
> 那不是 3D 的问题。`diag_palette.py` 已改为优先读 `canvas-<id>.png`。

#### W2 实施记录（2026-10-22，已落地）

材质做成**声明式字段**：`box` / `particle` 新增 `material?: MaterialKind`，
`world.stage.material` 控制台面。渲染层只做"预设打底 + 场景显式值覆盖"，
**没有任何 `if (def.id === ...)`**（宪法第六条）。

七种预设（`engine/materials.ts`，纯数据、可单测）：
`wood` / `linen` / `clay` / `metal` / `glass` / `jelly` / `chalk`。
贴图（`components/scene/textures.ts`）用 **固定种子的 LCG** 现画木纹与布纹——
不能用 `Math.random()`，否则每次刷新纹理不同，视觉回归永远失败。

**一条刻意保留的边界**：`material` 只给**有体积的实物**。矢量箭头、场线、轨迹是
物理量的图形化，给它们贴木纹会让"这条线代表 E"的约定失效。所以杆、绳、轨道
仍然是线框——这不是没做完，是设计。

三个金标准场景的分配与实测：

| 场景 | 材质 | 参照物 | std_l | 均饱和 |
|---|---|---|---|---|
| `buoyancy` | 台面 wood + 方块 jelly | 木尺 | 0.152 → **0.170** | 0.280 → **0.303** |
| `lever` | 台面 wood + 钩码 metal | 木尺 | 0.206 → **0.238** | 0.313 → **0.345** |
| `shm` | 台面 wood + 摆球 glass | 铅笔 | 0.156 → **0.181** | 0.268 → **0.285** |

**W2 踩到三个坑：**

1. **贴图不能烤色相。** 第一版把木色画进贴图，材质 `color` 又乘一次——
   台面亮度从 L≈0.40 直接砸到 0.23，`std_l` 从 0.15 坍到 **0.035**，整块画面变灰。
   正确做法：贴图只画**明暗纹理**，底色接近白（≈0.95），色相交给 `color`。
2. **`clearcoat` 的旧默认值 0.4 必须保住。** 加了 `material` 之后，
   没有指定材质的 9 个场景若跟着变成 `clearcoat: 0`（预设缺省值），
   外观会**悄悄变化**。所以 `resolveMaterial(undefined)` 显式回落到 0.4，
   并写了一条测试锁住它——迁移必须是显式动作。
3. **层次来自方向光，环境光只负责"不黑"。** 环境光 0.72 / 主光 1.35 时画面很平
   （`std_l` 0.10）；把比例拉到 **0.55 / 1.95** 才有 0.17–0.24 的明暗层次。
   之前一直以为是材质不够，其实是光比不对。

**仍未达成**：`bright_ratio`。`buoyancy` / `shm` 是 0%（目标 1.5–6%），
因为这两个场景没有大面积光面物体——木台面、磨砂玻璃、20 cm 果冻块都不产生
足够多的 >0.75 像素。**这一项要留到 W4**（演出层的发光体 + 更贴近物体的光源），
不是材质能补的。

#### W3 实施记录（2026-10-22，已落地）

四件事，**全部只碰 `scale` 与 DOM，不碰任何几何数据**：

| 交互 | 实现 | 参数 |
|---|---|---|
| hover 抬升 | 缓动到 1.025（不用弹簧，否则鼠标划过会一直抖） | 时间常数 ≈ 60 ms |
| 点击回弹 | 阻尼弹簧：`k=260 / c=11`，约 200 ms 收敛，约 30% 过冲 | `1 → 0.93 → 1.02 → 1` |
| 参数挤压 | 同一套弹簧，但 y 压扁、xz 变胖（体积感才对） | 幅度按场景 `decor.squash`，默认 0.07 |
| 读数缓动 | 120 ms easeOutCubic | 见下面的坑 3 |
| 入场转场 | 180 ms 淡入 + `scale(1.03 → 1)`（纯 CSS） | 遵循 `prefers-reduced-motion` |

挤压**只作用于场景声明的 `decor.subject` 一个对象**（浮力=方块、杠杆=木杆、简谐=摆球），
不是所有物体一起抖——那样看起来像画面在震，而不是"我推动了它"。

**核心断言**（`engine/contract/decor.test.ts`，17 条）：
把 `decor` 整个删掉，`sample(t)` 在 5 个时刻（0 / ¼ / ½ / ⅚ / 1 周期）的输出
**逐值完全相同**。这一条通过，宪法第一条（物理正确）与第五条（`sample` 纯函数）
就同时获得了机器保证。

**W3 踩到三个坑：**

1. **写了一个"假通过"的测试。** `solveAt` 的签名是 `(spec, params, t)`，
   我写成了 `(spec, t, params)`——两边都传错，所以 `toEqual` 当然成立，
   测试全绿但什么都没验证。发现方式：另一条断言（"改参数后 scalars 应当变化"）
   先红了，顺着查才看到顺序反了。
   > 教训：**新写断言时先问"把它改坏，这个测试会不会红"。**
   > 不会红的断言等于注释。参数顺序写反是最典型的"两边一起错"。
2. **R3F 的 `onPointerOver` 可能被重渲染吃掉。** 现象是"点了有反应，hover 却没光标"。
   `onPointerOver` 只在"进入对象"的那一帧触发，而这次进入状态会被同一帧的重渲染
   覆盖。改法：**在事件回调里直接写 `gl.domElement.style.cursor`**，绕过 React 调度，
   并补 `onPointerMove` 兜底（若 hovered 已为真，`setState` 会被 React 跳过，无开销）。
3. **HUD 补间不能走 state。** 12–15 个读数若各自用 state 做 60 fps 补间，
   等于每秒 ~900 次 React 重渲染，纯为一个装饰效果。改成在 rAF 里直写
   `textContent`：不触发任何重渲染，帧率零影响。

**验证**：hover 命中物体时 canvas 光标变 `pointer`、移到空白处自动清空；
点击出现选中条；12 场景冒烟 0 console error。

**验收（git stash 对照实验，旧代码同配置取样）**：5 个场景 A=0.00%、B=0.00%
（A：intro 禁用时与旧代码逐像素一致；B：演出结束后逐像素回到"没有 intro"）。
**任务 4.5（同日第二轮）**：压暗时序修复并推广到全部场景——intro 窗口（无 intro
场景为前 1.6s）内不压暗，结束后 0.35s 缓动落地；A/B 门复测 5/5 通过（≤0.04%）。
实施中发现并修掉一个时序坑：store 初始 `stepIndex=-1` 的 `active=false` 窗口
会把"演出结束后再压暗"的 ramp 永久杀死（kill-switch 必须等宽限结束才生效）。

**补墨第一轮的两个实测结论（2026-10-25，任务 3）**：
1. **受光半透明体积不可用作区域示意**——Stage 灯把 0.14 透明度的物理材质盒子
   照成近白的一团雾，且深度写入把体积内的线条整个盖掉。契约 v0.5 因此新增
   `box.unlit`（无光照 + 不写深度 + 双面）。
2. **细线加宽 + 光晕层的天花板约 2% 墨迹**（projectile/wave/orbit/reflection/
   thin-lens/electric-field 全部落在 1.7–2.0%）；lorentz 之所以达标 3.5%，
   靠的是 unlit 雾墙这个**体积元素**。剩余场景的第二轮补墨以体积元素为主。

**三条材质纪律（每条都是踩出来的，写在 `applyIntroAlpha` 注释里）**：

1. **演出没开就一次都不碰 opacity。** HighlightGroup 的"聚焦某一步"会把其他物体
   压到 opacity 0.14——逐帧覆盖会让聚焦失效（实测 lorentz 旧帧是压暗态、新帧全亮）。
2. **演出结束就撒手。** 只恢复一次基准值（且要读 `__dim` 取压暗值），之后不再逐帧写。
3. **`transparent` 变化必须标 `needsUpdate`。** 它在 three 的 program 缓存键里，
   不标脏会让材质继续用旧 shader 变体（实测方块区域残留 1% 竖带）。

**顺带修正一个更早的测量错误（比 intro 本身更重要）**：
虚拟时钟的泵帧步长必须 ≤50ms（`SceneRuntime` 与 intro 都有 `Math.min(delta, 0.05)`
的 dt 钳制）。原先用"一次 `__advance(167ms)` 泵 10 帧"，被钳成 50ms——
**整个时钟按比例放慢到 1/3，而捕获仍然确定**，所以从不报错，只是"t=3.0"实际是
t≈0.9（intro 永远演不完）。现在改为页面内逐帧泵（`__advanceFrames`），
HUD 时间与标称值逐位对齐。

**新发现（转给内容阶段的任务 4.5）**：多数场景讲解脚本第 0 步就带 `highlight`，
于是开场 1.6 秒里几乎所有物体都处在压暗态——**开场演出是在一张 0.14 不透明度的
画里演的**。墨迹占比不受影响（0.2–0.3% 不变），但视觉对比度塌了。
W4 内容阶段要么让第 0 步不压暗，要么把演出排在首次高亮之前。

## 6. 浅色模式改造（2026-10-22，已落地）

产品负责人决定**整体切浅色**（不是加第二套主题），理由是课堂投影：明亮教室里
投影仪打深色背景会发灰、对比度塌陷，浅色底反而更稳。这条也写进了 §3.2。

因为是"替换"而不是"叠加"，工作量约为双主题方案的六成 —— 不需要写暗色变体，
也不需要维护双份视觉基线。

### 6.1 改了什么

| 层 | 内容 |
|---|---|
| CSS token | `globals.css` 重写：暖白纸感底 `#f6f3ee`、stone 暖灰文字、强调色统一降到 600/700 档、`color-scheme: light` |
| 组件类名 | `scripts/theme_light.py` 按显式映射表替换 **319 处 / 19 个文件** |
| 曲线图 | 序列色从 400 档改 600 档（白底上 `#22d3ee` 对比度只有 1.9:1，`#0e7490` 是 4.9:1） |
| 3D 环境 | 程序化环境贴图从冷蓝夜空改成暖白室内光；尘埃从"叠加亮点"改成"普通混合暗点" |
| 3D 光照 | 霓虹点光（强度 26/16）改成室内顶光 + 微弱冷暖补光；泛光阈值 0.6 → 0.88 |
| 画布底板 | **所有场景**都画背景板（原来靠透明画布 + 深色页面充当"虚空"） |

### 6.2 踩到三个坑

1. **浅色页面下透明画布会让 3D 内容"消失"。** 深色模式时画布是透明的，
   页面深色背景正好充当框住内容的"虚空"；页面变浅后，细线直接漂在白纸上，
   实测均亮 0.98、99% 像素接近纯白。修法：给一块比页面深三档的**中间调底板**
   （`#8e8574`），3D 内容才有地方落下阴影和高光。
2. **环境光是层次的敌人。** 切浅色后一度把 hemisphere 提到 0.9，结果 std_l 只有
   0.06 —— 阴影全被填平，画面像一张灰纸。压到 **0.55**、主光提到 **2.5/2.9**
   之后 std_l 回到 0.10–0.12。这和 W2 的结论是同一条：**层次来自方向光，
   环境光只负责"不脏"。**
3. **`std_l` 的目标值本身定错了。** 原来要求 ≥0.14，但参考站（密集微缩实景）
   本身只有 **0.111**。物理示意图是"中间调底板 + 细线主体"，天生比实景平。
   拿 0.14 去要求它，等于在追一个参照物都没达到的数字。已把下限改成 0.10。

### 6.3 改造后实测（纯画布口径）

| 场景 | 均亮 | 暗部 | 亮度std | 均饱和 | 高光 |
|---|---|---|---|---|---|
| `buoyancy` | 0.081 → **0.627** | 0.0% | 0.089 → **0.111** | 0.478 → **0.265** | 6.0% |
| `lever` | 0.081 → **0.542** | 0.0% | 0.089 → **0.113** | 0.478 → **0.229** | 5.5% |
| `shm` | 0.079 → **0.599** | 0.0% | 0.080 → **0.119** | 0.458 → **0.201** | 5.3% |
| `orbit` | 0.076 → **0.514** | 0.0% | 0.076 → **0.105** | 0.490 → **0.123** | 5.3% |
| `wave` | 0.072 → **0.513** | 0.0% | 0.067 → **0.105** | 0.491 → **0.124** | 5.4% |

均值 **0.559**，参考站 0.577 —— 已经对标上。饱和度从 0.48 降到 0.19，
这是"廉价感"消失的主要来源。

> 遗留一项：`buoyancy` 均值 0.627，超上限 0.007（噪声范围内）。
> 不追了 —— 为 0.007 再调一轮光照，收益不值得。

### 6.4 这次改造**没有**做的事

- ❌ 没做深色模式开关。现在是单一浅色主题，`data-theme` 之类的机制没搭。
  如果将来要双主题，§6.1 的 token 层可以直接复用。
- ❌ 没做投影环境实测。所有结论都基于"截图统计 + 参考站对标"，
  真实投影仪上的效果需要拿教室机器验一次。
- ❌ 场景内容里的 171 个 hex 一个没改。矢量色（青/橙/粉）在白底上仍偏亮，
  需要一层渲染期的对比度映射表 —— 这是 W5 的活儿，已记进待办。

## 8. 验收指标（可自动化）

| 指标 | 现在 | 目标 | 测法 |
|---|---|---|---|
| 平均亮度 L | 0.072–0.109 | **0.30 – 0.42** | `diag_palette.py`（本次新增） |
| 暗部占比（L<0.08） | 68–90% | **< 25%** | 同上 |
| 亮度标准差 | 0.065–0.135 | **0.16 – 0.24** | 同上（**刻意高于参考站的 0.111**：深色外壳 + 亮展台 = 更大对比） |
| 平均饱和度 S | 0.458–0.538 | **0.20 – 0.32** | 同上 |
| 高光占比（L>0.75） | 0.1–1.0% | **1.5% – 6%** | 同上 |
| 主体占高 | 30–65% | **≥ 62%** | `shot_canvas.py` 量 bbox |
| 阴影覆盖 | 0 | **每场景 ≥1 处可见投影** | 人工 + 主光投影区域像素暗于周围 8% |
| 材质种类 | 1 | **每场景 ≥ 3** | 查 spec 的 `material` 字段集合 |
| 帧率（中端安卓） | 未测 | **≥ 30 fps** | 新增 `diag_fps.py`（rAF 间隔采集） |
| 首屏 JS | 103–130 kB | **≤ 200 kB**（宪法七） | `next build` 报告 |

### 8.1 不许为了达标而牺牲

- ❌ 不准靠"提亮背景"把均亮刷上去（那是把黑底换成灰底，物体依然没有质感）
- ❌ 不准靠"降饱和"把饱和度指标刷下去（会出现一片灰）
- ❌ 不准为了照片好看而移动物理几何（宪法第一条）
- ❌ 不准关闭阴影换来帧率达标（阴影是本轮的核心交付物）

### 8.2 最终判据（人）

> 把 12 个场景的默认帧拼成一张 3×4 的图，给 3 位没看过产品的人看 10 秒，
> 问"这是什么"。答案应该是「一个能动手的物理教具」，
> 不能是「一堆代码/一堆线」。

## 9. 性能预算与质量分级

宪法第七条：中端安卓 ≥30fps，单帧求解 ≤2ms，draw call ≤150。

新增的 GPU 开销都来自：阴影贴图、`transmission`（每次额外 render target）、台面几何。

| 档位 | 触发条件 | 阴影 | transmission | bloom | 台面 | 接触阴影 |
|---|---|---|---|---|---|---|
| **高** | 桌面 / dpr ≥ 1.5 / 独显 | PCFSoft 1024 | ✅ | ✅ 0.18 | 完整（含木纹） | 贴图 |
| **中** | 移动端 / dpr 1–1.5 | PCF 512 | ❌ 降为 `opacity` | ✅ 0.12 | 纯色 | 贴图 |
| **低** | `prefers-reduced-motion` 或连续 3 秒 <24fps | ❌ | ❌ | ❌ | 纯色无纹理 | 贴图 |

自动降级策略：启动后 3 秒内采样 rAF 间隔，中位数 < 24fps 则自动降一档，
并在角落提示一次"已切换到流畅模式"（可手动改回）。

> 这一条必须是 W6 的**硬交付**，不能留到"以后优化"。
> 校园机房的真实硬件比开发机差一个数量级，降级没做好等于把新增的画面全赔进去。

## 10. 与八条宪法的冲突检查

| 条 | 冲突点 | 处理 |
|---|---|---|
| 一 · 物理正确 > 视觉 | 挤压/回弹/水花属于"演出" | 全部隔离到 `decor` 层；`sample(t)` 输出的 points/vectors 一个字不变；加断言：关闭 `decor` 后 spec 输出哈希一致 |
| 二 · 不等于不变量测试 | 视觉无法写不变量 | 用**色彩/几何统计**代替（§8），并把 §4.5 构图规则 1–4 写成契约测试 |
| 三 · 诚实声明假设 | 半透明水/玻璃会让人以为"看得准" | `assumptions` 增加一条："水与玻璃为示意材质，折射率与厚度不参与计算" |
| 四 · 只有必须才做 3D | 无冲突 | — |
| 五 · `sample(t)` 纯函数 | 演出层若依赖随机/时间会破坏 | 演出层用**独立时钟**，不进入 solver；`decor` 关闭时 solver 完全不受影响 |
| 六 · 内容即数据 | 材质/舞台必须先做成**图元字段** | 新增 `material` / `world.stage` 契约字段，而不是在渲染层写场景分支 |
| 七 · 性能预算 | 阴影 + transmission 是新增开销 | §9 三档降级 + 自动切换 |
| 八 · 零外部资源 | 材质纹理不能下载 | 全部 `CanvasTexture` / 顶点色 / 程序化噪声；**不新增任何图片文件** |

> 第六条值得强调：材质必须做成**声明式字段**。一旦允许"在 `objects.tsx` 里
> `if (def.id === 'block') return <Jelly/>`"，12 个场景就会退化成 12 段特判代码，
> 宪法第六条当场失效。

## 11. 风险

| 风险 | 等级 | 影响 | 对策 |
|---|---|---|---|
| 阴影 + transmission 把帧率打崩 | 🔴 高 | 校园机不可用 | §9 三档 + 启动测速自动降级；W1 就先测帧率，不留到 W6 |
| 半透明材质让物理量看不清 | 🔴 高 | 教学失效 | 物理矢量永远不透明、永远在 `renderOrder` 最上层 |
| 12 个场景迁移工作量超预期 | 🟠 中 | 拖期 | 先迁 3 个（`buoyancy`/`lever`/`shm`）作为"金标准"，再批量 |
| 暖色 + 低饱和变成"一片糊" | 🟠 中 | 观感变差 | §8 的高光占比与亮度 std 是护栏；每批迁移后必跑 palette 统计 |
| 程序化木纹/布纹做不像 | 🟠 中 | 更假 | 先做 1 个材质，A/B 对比；做不像就退回"纯色 + 接触阴影"，不硬凑 |
| 演出层破坏 `sample(t)` 纯函数 | 🟠 中 | 违反宪法五 | 演出层用独立时钟；加"关 decor 输出一致"的断言 |

## 12. 非目标

- ❌ **不做 WebGPU**。校园老机器 + 微信内置浏览器不支持，收益不抵可用性损失。
- ❌ **不引入物理引擎**（rapier/cannon）做软体。宪法五/一都不允许；趣味靠"演出层"给。
- ❌ **不做角色/表情/宠物**。物理教具加人格容易滑向玩具，先不碰。
- ❌ **不做整体浅色主题**。页面 chrome 保持深色，只把画布做成亮展台（成本与一致性）。
- ❌ **不新增任何图片/模型文件**（宪法八）。材质全程序化。
- ❌ **不做音效**。课堂环境里默认静音等于没做，默认有声又要做开关与合规，放 M3.5 再看。
- ❌ **不改动求解器与物理数值**。本轮只改渲染层与内容声明。

## 13. Go / No-Go

| 关卡 | 时点 | 通过条件 | 不通过 |
|---|---|---|---|
| **G1 地基成立** | W1 末 | 3 个参考场景（浮力/杠杆/简谐）截图达标：暗部 <35%、有可见投影、主体 ≥62%；帧率中端安卓 ≥28fps | 回退到"只开阴影 + 暖色背景"的最小方案，不做材质 |
| **G2 材质成立** | W2 末 | 6 种材质肉眼可分；12 场景 ≥3 材质；无"更假"的材质 | 砍掉 `wood`/`linen` 的程序化细节，改纯色 |
| **G3 趣味成立** | W4 末 | 12 个入场动画可截出 12 张封面图；`sample()` 输出哈希与 M2 完全一致 | 只保留 4–6 个最好的，其余不做 |
| **G4 全部达成** | W6 末 | §8 全部指标达标 + §8.2 人工判据通过 | 不进入 M4，继续打磨 |

> **G3 的"输出哈希一致"是本计划最重要的一条断言。**
> 它把"加了很多动画"和"物理一点没变"这两件事同时钉住——
> 这一条测试通过，宪法第一条与第五条就同时得到了机器保证。
