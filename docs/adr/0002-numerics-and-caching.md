# ADR-0002 · 数值方法与缓存策略

---

## 背景

教学场景对"物理"的要求与游戏/仿真软件不同。游戏要**看起来真实**，允许近似、允许阻尼、
允许攒误差；教学要**和课本对得上**，而且必须支持：

1. 时间轴任意拖拽、倍速、回退
2. 讲解脚本"跳到最高点那一帧"暂停
3. 参数每次改动都可复现
4. 学生在 3 年前的手机上拖动滑块不卡

这四条约束叠加，直接排除了「用物理引擎逐帧推进」这条路。

---

## 决策

### 1. 优先解析解，其次定点重放，最后才是实时积分

| 场景类型 | 方法 | 例子 |
|---|---|---|
| 有闭式解 | 解析解，`sample(t)` 直接代公式 | 抛体、洛伦兹（含螺旋）、薄透镜成像 |
| 无闭式解但确定 | 参数变更时**预计算整条轨迹**，`sample(t)` 只做查表插值 | 试探电荷在双电荷场中的运动 |
| 场量（与时间无关） | 参数变更时一次性计算几何，缓存 | 电场线、等势线 |

**关键**：把"时间推进"从求解里彻底移除。时间只是一个查询参数，不是状态。

### 2. 场线用 RK4 沿弧长积分，而不是欧拉

`dr/ds = Ê(r)` 是单位矢量场，RK4 在 `h = 0.22 m` 时角度误差 < 1e-4 rad，
足以让"场线与等势线垂直"的断言通过。欧拉法在电荷附近会明显弯折，视觉上肉眼可见。

### 3. 等势线用 marching squares + 线段拼接

网格 132×132（`x,z ∈ [-14,14]`），线性插值。拼接成折线是必须的：
直接渲染上百个 2 点线段会产生上百个 draw call，在移动端直接掉到 20 fps。

### 4. 缓存按"参数字典序"生成 key，命中时返回**原引用**

```ts
const key = Object.keys(params).sort().map((k) => `${k}=${params[k]}`).join('|');
```

返回原引用（而不是 clone）是渲染层的约定：`polylines` 组件通过比较数组引用判断
「是否需要重建几何」。这样播放过程中每帧 `sample()` 都不触发 React 重渲染。

缓存上限 8 条，FIFO 淘汰——滑块快速拖动时不至于无限增长。

## 备选方案与被否原因

| 方案 | 否决原因 |
|---|---|
| rapier / cannon 物理引擎 | 逐帧推进不可回退；固定步长攒误差；无法保证 `r = mv⊥/qB` 精确到 1e-9；包体积 +600 KB |
| Web Worker 实时积分 | 仍然解决不了"拖时间轴"的可复现性；且增加通信延迟与调试成本 |
| WASM 物理库 | 同上，且破坏"零外部依赖、可离线"（宪法第八条） |
| 预烘焙轨迹数据（JSON） | 参数一改就要重算，等于把问题挪到构建期；且无法覆盖连续参数空间 |

---

## 后果

**好处**
- 任意跳帧、倍速、回退都是免费的
- 单测可以拿公式直接对，精度到 1e-9
- 播放时每帧只做查表，移动端友好

**代价**
- 每个求解器都要自己写物理，不能"接入引擎了事"——这是刻意的：**写不出公式说明没理解物理**
- 缓存逻辑带来一类新 bug（key 漏参数 → 调参无反应），因此 SPEC-011 要求「参数死值检测」测试
- 非线性系统（三体、混沌）不适合这套方法；真要做，就得允许"实时模式"并明确标注不可回退

## 反悔条件

出现以下任一情况，应重新评估：

1. 需要真实碰撞/摩擦/多体接触（如"滑块在斜面上"），解析解写不出来且误差敏感；
2. 单个场景的预计算时间 > 200 ms（参数拖动会卡顿）；
3. 需要"用户实时拖动物体并得到物理响应"的交互（如拖拽电荷后场线实时跟随）。

第 3 条最有可能先出现。届时的折中方案是：**拖动过程用粗网格低精度场线，松手后补算高精度**。
