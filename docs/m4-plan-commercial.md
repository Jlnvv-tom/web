## 0. 先明确：M3 要验证什么

M2 已经把「真 3D + 讲解脚本 + 调参 + 离线导出」全部免费给完了。所以 M3 不能再靠"更多 3D"卖钱。

**M3 的唯一假设：**

> 教师愿意为「**布置作业 + 看到全班哪道题错了**」付 99–199 元/年。

判据不是"注册了多少人"，而是：

| 判据 | 目标 | 为什么是这条 |
|---|---|---|
| 收到第一笔真实付款 | ≥ 1 笔 | 免费用户说"好用"没有信息量，掏钱才有 |
| 连续两个学期使用同一份作业 | ≥ 3 位教师 | 证明它进了教学流程，而不是一次性尝鲜 |
| 作业提交率（提交数 / 班级人数） | ≥ 50% | 学生不愿交，说明答题体验或激励有问题 |

> 若 3 个月内"付款 ≥1 笔"与"3 位教师连续使用"都达不成，**M3 应停止扩张并回退**，
> 把精力放回内容（初中端还只有 3 个场景）。这条退出条件写在计划里，是为了防止
> "既然做了后端就继续做完"的沉没成本陷阱。

## 2. 三条红线（违反即否决方案）

### 红线一 · 教学主路径不依赖后端

宪法第八条的延伸。引入后端最大的风险不是技术，是**把原本纯静态的产品做成"必须联网"。**

| 必须保持零后端 | 可以依赖后端 |
|---|---|
| `/topics/*` 12 个知识点页 | 登录 / 收藏同步 |
| 学生看讲解、拖参数、做练习 | 班级作业提交与汇总 |
| 导出离线单文件 HTML | 教师后台统计 |
| 断网下全部教学功能 | 计费与授权 |

**落地检查**：`next build` 仍要产出完整 `out/`，把后端域名拉黑（hosts / Playwright 拦截）
之后，12 个场景的冒烟必须照样 12/12 通过。这条做成 CI 断言，不是口号。

> 反例（明确禁止）：把"账号"做成进入播放器的前置条件；把 HUD 数据改成服务端算。

### 红线二 · 学生零个人信息

市场报告的结论是「教师最讨厌给每个学生注册账号」，而且未成年学生信息一旦收集，
合规成本会指数上升。所以：

- 学生**不注册、不填姓名、不填学号**
- 作业提交只带服务端下发的一次性匿名码
- 后台只显示「匿名 1 / 匿名 2 …」与聚合正确率
- 教师若要对应到人，**由教师在纸面上自己映射**，系统不留姓名

### 红线三 · 后端只做增值旁路

后端故障时，页面必须降级为"静态站 + 一个温和提示"，而不是白屏或报错页。

## 3. 角色与权限

| 角色 | 是否注册 | 身份凭据 | 能做什么 |
|---|---|---|---|
| **学生** | ❌ 否 | 服务端下发的一次性 anon 码 | 打开作业、作答、提交（在线或离线答题卡） |
| **教师** | ✅ 是 | 微信扫码（OAuth） | 建班、布置作业、看热力图、导出、管理授权 |
| **家长** | — | — | 不参与 M3 |
| **教研员 / 学校** | ⏳ 后续 | 组织账号 | 跨教师查看（M4 再议） |
| **管理员** | ✅ 内部 | 白名单 + 2FA | 审核内容、查审计日志、手动发授权 |

权限模型用**资源归属 + 显式授权**两段式，不上 RBAC 框架：
`teacher owns classroom → classroom owns assignment → assignment owns submissions`。
每条查询都必须带 `teacher_id` 条件，靠一个仓储层函数强制，禁止裸 SQL 直出。

### M3.2 · 班级作业（3.0 周）⭐ 核心

这是 M3 存在的理由，也是唯一值得付费的功能。

#### 4.2.1 教师侧流程

```text
新建班级（名称 + 年级 + 教材版本）
  → 布置作业：选 1–6 个知识点，每个知识点挂 1–3 道预测题
  → 得到 6 位作业码（如 K7M2QP）与二维码
  → 学生作答（在线 / 离线答题卡）
  → 热力图：每个选项的分布 + 每个知识点的掌握率
```

#### 4.2.2 学生侧流程（不注册）

```text
扫二维码 / 输 6 位码 →（服务端下发一次性 anon 码，写 Cookie）
  → 看到第 1 题（先预测，不能跳）
  → 提交 → 立刻看到解释 + 可点「在 3D 里验证」（复用现有 POE 组件）
  → 全部提交完显示「已提交，共 N 题」
```

关键设计：**答题过程不打断 3D 体验**。学生答错后可以直接跳进对应场景拖参数看现象——
这是和"问卷星式作业"的根本区别，也是教师愿意用的原因。

#### 4.2.3 离线答题卡（差异化功能，也是"无网教室"兜底）

复用 M2 的离线导出管线（[F-013](./specs/013-offline-export.spec.md)）：

| 步骤 | 教师 | 学生 |
|---|---|---|
| 1 | 导出 `assignment-K7M2QP.html`（含场景 + 题目，**单个 HTML**） | — |
| 2 | 拷到 U 盘 / 机房共享盘 / 班级群 | 双击打开，作答 |
| 3 | 后台「导入答案」 | 点「导出我的答案」→ `answer-K7M2QP-a1b2.json` |
| 4 | 汇总进同一张热力图 | — |

这条看起来"逆潮流"，但它把**机房无网 / 手机被收 / 家长不让装 App** 三种真实场景都覆盖了，
而且几乎零额外后端成本（导入接口只解析 JSON）。**建议和在线模式同期做，不要留到后面。**

## 5. 数据模型

```sql
-- 教师（唯一需要注册的角色）
teacher(id, wx_openid UNIQUE, wx_unionid, nickname, avatar_url,
        plan ENUM('free','teacher','trial'), plan_expire_at,
        created_at, deleted_at)

-- 班级
classroom(id, teacher_id → teacher, name, grade, textbook_version,
          join_code UNIQUE, archived_at, created_at)

-- 作业
assignment(id, classroom_id → classroom, title, code UNIQUE,
           status ENUM('draft','open','closed'), due_at,
           allow_offline BOOL, created_at)

-- 作业题目（引用已有场景 + 已有 quiz，不新造题目内容）
assignment_item(id, assignment_id, seq, scene_id, quiz_index)

-- 提交（学生，无个人信息）
submission(id, assignment_id, anon_code, submit_key UNIQUE,   -- 幂等
           source ENUM('online','offline_file'),
           started_at, submitted_at, ua_hash)

submission_answer(id, submission_id, item_id, picked, correct)

-- 授权与审计
entitlement(id, teacher_id, plan, granted_by, granted_at, note)
audit_log(id, actor_teacher_id, action, target_type, target_id, ip_hash, at)
```

设计要点：

1. **作业题目只引用、不复制**。`(scene_id, quiz_index)` 指向 `content/scenes/*` 里已有的
   `quiz` 条目——这样 12 个场景的题目内容仍然是"内容即数据"（宪法第六条），
   M3 不引入第二套题目体系。**若将来要支持教师自编题，另开 M4。**
2. `anon_code` 由服务端生成，不含任何可推导学生的信息；`ua_hash` 只用于防刷，不对外展示。
3. `submit_key` 幂等：`hash(assignment_id + anon_code + source)`，重复提交更新而非新增。

## 6. 技术选型与 ADR

现状：纯静态 Next.js 15 导出，无运行时、无数据库。M3 要引入第一块有状态的东西，
必须走 ADR，不能"顺手就选"。

### 6.1 候选项

| 方案 | 优点 | 缺点 | 适配度 |
|---|---|---|---|
| **A. Next.js 改为 Node 运行时 + Postgres** | 复用现有代码、类型共享、一套部署 | 失去纯静态导出（与红线一冲突，需双构建） | ⭐⭐⭐⭐ |
| B. 静态站 + 独立 Serverless（云函数 + 托管 PG） | 静态站原封不动，后端完全旁路 | 两套仓库/两套类型，易漂移 | ⭐⭐⭐⭐ |
| C. Supabase / Firebase | 开箱鉴权 + 数据库 + 存储 | 数据在境外 / 需自建替代；微信登录要自己接 | ⭐⭐ |
| D. 自建 VPS + Postgres + 轻框架 | 完全可控、成本最低 | 运维全包，单人项目负担重 | ⭐⭐⭐ |

### 6.2 倾向方案：B（静态站 + 独立旁路 API）

理由，按重要性排序：

1. **红线一天然满足**。静态站一行不改，`out/` 仍可拷 U 盘、仍能断网跑。
   方案 A 要在"同一份代码出静态 + 出动态"之间反复切换，最容易在某次构建里悄悄破功。
2. **失败可弃**。如果 M3 假设不成立，直接关掉 API 域名，产品回到 M2 的完整状态，
   不留下"半动态"的技术债。
3. **类型共享可以靠生成**。后端用 TS + zod，用一个脚本把 API schema（OpenAPI）
   生成前端 client，避免两套手写类型漂移。

> 若最终选 A，必须在 ADR 里写清"如何保证导出产物不依赖运行时"，并附 CI 证明。

### 6.3 ADR 清单（M3 开工前必须写完）

| ADR | 议题 | 关键决策点 |
|---|---|---|
| 0003 | 后端形态与部署 | B 还是 A；托管区域（境内，备案要求） |
| 0004 | 身份与授权 | 微信 OAuth 的 openid/unionid 取舍；会话用 Cookie 还是 Bearer |
| 0005 | 匿名与幂等 | anon_code 生成策略、防刷强度、是否需要设备指纹 |
| 0006 | 埋点去向 | 本地埋点是否上报、以何种形式、同意流程 |
| 0007 | 支付与授权 | 手动授权码 → 正规支付的分阶段方案 |

## 7. 测试策略（新增 L5）

现有 L1–L4 全部保留。M3 新增一层：

| 层 | 内容 | 工具 | 红线 |
|---|---|---|---|
| **L5 后端契约与权限** | 每个接口的鉴权矩阵、越权访问、幂等、并发提交 | vitest + 真实临时库 | 越权用例必须 100% 覆盖 |
| **L5b 离线一致性** | 离线答题卡导入与在线提交产出**同一份**热力图 | Playwright + 快照 | 逐题比对，不允许"大致一致" |
| **L4 增强** | 拉黑后端域名后，12 场景仍 12/12 | Playwright route abort | 破红线一即失败 |

**权限矩阵测试是重点**。做法：一张表 `(角色 × 资源 × 动作) → 期望状态码`，
用 `it.each` 全量跑一遍。这类测试的价值在于**新增接口时强制补一行**，
漏补就会在"新增接口必须有权限用例"的断言里失败。

## 9. 计价与商业模型

### 9.1 版本设计

| 版本 | 价格 | 包含 | 目的 |
|---|---|---|---|
| 免费 | 0 | 全部 12 个场景、离线导出、**1 个班 + 1 份作业** | 让教师完整体验一次闭环 |

| 学校版 | 按教师数报价（≥ 5 位 8 折） | 组织账号、跨教师汇总 | M4 |

定价依据：市场报告里 NOBOOK 单科年卡 298 元、Gizmos 教师版 $599–799/年。
149 元的定位是"教师个人掏得起、不用报账"，避免触发学校采购流程。

### 9.2 支付的现实约束（必须提前决策）

个人开发者**开不了微信支付商户号**。所以分两阶段：

| 阶段 | 方式 | 缺点 | 何时切换 |
|---|---|---|---|
| M3.3 首版 | **人工授权码**：教师转账/赞赏码付款 → 管理员后台手动发放授权码 | 需要人工，约 1 分钟/单 | 直到月单量 > 30 |
| M3.4+ | 正规支付（个体户/公司主体 + 微信支付） | 需要资质与对账开发 | 资质下来后 |

> 人工发放听起来很土，但它是**验证付费意愿最快的路径**：
> 前 10 单人工处理的总成本不到 1 小时，却能在写支付代码之前就知道有没有人愿意掏钱。
> 这也是 §0 那条判据"收到第一笔真实付款"能最快达成的做法。

## 12. 非目标（明确不做）

- ❌ **学生账号**。任何"让学生注册"的方案直接否决，理由见红线二。
- ❌ **UGC / 社区 / 评论**。合规与运营成本都扛不住。
- ❌ **教师自编题目**。题目仍来自 `content/scenes/*` 的 `quiz`，保证物理正确性可审计。
  自编题 = 第二套内容体系 + 审核流程，M4 再议。
- ❌ **实时课堂（学生同步答题大屏）**。需要长连接与并发设计，收益不确定。
- ❌ **AI 讲解助手（M16）**。成本不可控，且与"离线可用"冲突。
- ❌ **学校 / 区域采购**。要招投标与资质，M4 之后。
- ❌ **服务端渲染场景**。场景永远在客户端算（宪法第五条：`sample(t)` 必须纯函数）。

## 13. 与 M2 的衔接

M3 不是从零开始，直接复用：

| M2 已有 | M3 怎么用 |
|---|---|
| 离线单文件导出（F-013） | 离线答题卡 = 同一管线 + 作业数据 |
| 本地埋点（F-014） | 教师在后台"自愿分享使用数据"时按需上报（ADR-0006） |
| `quiz` 数据结构 | 作业题目直接引用 `(scene_id, quiz_index)` |
| POE「验证」按钮 | 学生答错后一键跳进场景看现象 |
| 12 个场景 + 章节树 | 布置作业时按章节树选题 |

**一个具体的复用点值得强调**：F-013 的运行时共享方案（一份 `runtime.js` + 场景 JSON）
意味着离线答题卡不需要新的构建管线，只需要在 JSON 里多带一份 `assignment` 字段。
这是 M2 那个决策的延迟收益。
